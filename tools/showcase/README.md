# Showcase tools

The top of the main [README](../../README.md) is the app's showcase: a
walkthrough video, screens, a day-by-day timeline and the latest builds. All
of it lives in [`showcase/`](../../showcase) and is generated by these scripts
from the running app, so it can be rebuilt whenever the app changes.

| Script | Makes | When to run it |
|---|---|---|
| `capture.mjs` | `showcase/screens/`, the two contact sheets, and the walkthrough video with its teaser and poster | after any change a user would see (`--shots` skips the video) |
| `timeline.mjs [YYYY-MM-DD ...]` | `showcase/timeline/<day>.jpg` and the timelapse | after a day of visible changes, for that day only |
| `buildlog.py` | `showcase/BUILDLOG.md`, and the "Latest builds" block in the main README | every time the showcase is refreshed |

```bash
node tools/showcase/capture.mjs
node tools/showcase/timeline.mjs 2026-10-14
python3 tools/showcase/buildlog.py
```

Then check the README's captions still describe what the pictures show, and
commit the lot together.

## How they work

They need Google Chrome and ffmpeg, both already on the development Mac, and
ImageMagick (`magick`) for the sheets and the timeline. Nothing is installed.
Chrome is driven headless through its own DevTools protocol (`chrome.mjs`;
Node 22 or later). Set `CHROME=` if Chrome lives elsewhere.

- **The app runs on its own port, with a throwaway session.** Neither the real
  session file nor a running demo is touched. The screens use the "practice"
  example, a made-up psychology practice; dates follow the day they are taken.
- **The walkthrough is built from stills,** each held for as long as it should
  be on screen, with scrolls, fades and taps drawn in even steps. A slow or
  busy machine makes the script take longer, never the video stutter.
- **The timeline runs each day's own code.** The day's last commit is checked
  out into a scratch worktree and started with its own packages first on the
  path. Only committed history is captured, never the working tree. Before 6
  October the frame is the developer's desktop page; from then on, the phone.
- **A step whose button has gone stops the script and names it.** That is how
  you learn the showcase is out of date: update the screen list or the
  walkthrough in `capture.mjs`, and the README's captions, to match.
- **The build log is built from which paths changed, never from commit
  messages.** A path no rule recognises is counted, not printed; a new kind of
  file needs a rule in `classify()`. It is rebuilt from the whole history each
  time, so it is always consistent; a commit cannot list itself, so the log
  runs up to the commit before the one that refreshes it.

## Pushing

The media make a showcase commit a few megabytes. If a push fails with
`HTTP 400` / "the remote end hung up", raise git's upload buffer for that push:

```bash
git -c http.postBuffer=157286400 push
```
